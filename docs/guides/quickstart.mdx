Get two nodes talking on your machine, and watch the routing model change in
response to what happens.

<Note>
NTL is in active development. Everything below is real and runs today, but the
CLI and API are not yet stable.
</Note>

## Prerequisites

- Node 18+ (for the npm install) **or** Rust 1.85+ ([install](https://rustup.rs))
- A terminal

## Install

```bash
npm install -g @nyuchi/ntl-cli
ntl --version
```

The CLI is a Rust binary; npm is just the distribution channel, because it is
the package manager almost everyone already has. The postinstall step downloads
the binary for your platform and verifies its SHA-256 checksum.

Prefer Rust, or on a platform without a prebuilt binary:

```bash
cargo install --git https://github.com/openNTL/ntl ntl-cli
```

## Initialize a Node

```bash
ntl init
```

This creates, under `~/.ntl` (override with `--home` or `$NTL_HOME`):

| Path | What it is |
|---|---|
| `config.toml` | Node configuration, with edge-class defaults |
| `node.db` | SQLite store — identity, synapses, journal, dedup cache |

Output:

```text
✓ node initialized
  home      /home/you/.ntl
  config    /home/you/.ntl/config.toml
  store     /home/you/.ntl/node.db (sqlite)
  class     edge
  identity  843d9ad69b4f

Next: ntl start --dev
```

The identity is a keypair derived from a seed in the store. It **persists** —
a node that regenerated its identity on each start would lose every synapse
it had formed and relearn its routing from scratch every restart.

Pick a different deployment class with `--class edge | full-node |
high-traffic`. The class sets learning rate, queue depth, refractory period,
and fanout together, so the combination stays coherent.

## Two Nodes, One Signal

NTL is peer-to-peer with no broker, so the smallest interesting network is
two nodes. Use two terminals.

**Terminal 1 — the receiver:**

```bash
export NTL_HOME=~/.ntl-b
ntl init
ntl listen --listen 127.0.0.1:14433
```

**Terminal 2 — the sender:**

```bash
ntl emit --type data --payload '{"hello":"world"}' \
         --acknowledged --peer 127.0.0.1:14433
```

The sender prints:

```text
→ emitted 01M0QEC1F14QY9DTFH2BQQEJJK (data, weight 0.5)
+ peer connected ntl:daef80390ccfa3f4...
→ forwarded 01M0QEC1F14QY9DTFH2BQQEJJK to 1 peer(s)
✓ receipt delivered weight +0.0322
```

And the receiver:

```text
← 01M0QEC1F14QY9DTFH2BQQEJJK Data weight 0.450 from ntl:843d9ad69b4f...
  {"hello":"world"}
```

Three things in that exchange are worth pausing on.

**`weight 0.450`, not `0.500`.** The signal was attenuated by the synapse it
crossed (`0.5 × 0.9`). Weight decays with distance, which is what stops a
flood from travelling forever.

**`--acknowledged`.** Without it the signal is `best-effort`: it may be
absorbed silently and the sender never learns. With it, the sender is
guaranteed an outcome — a receipt or a timeout, never silence. Use it for
anything with a side effect. See
[delivery-semantics](/spec/delivery-semantics).

**`weight +0.0322`.** That is the routing model updating. The receipt came
back, resolved the journalled routing decision, and strengthened the synapse
that carried it. Emit again and it rises again — bounded by the total weight
budget and the per-peer influence cap.

## Watch the Model

```bash
ntl synapses
```

```text
PEER             WEIGHT      STATE SENT/RECV     ERR  AFFINITY
daef80390ccf     0.1322     active 1/0          0.00  Data:1

total outbound weight 0.1322 of 8.0 budget
```

`WEIGHT` is learned, not configured. `AFFINITY` is learned per signal type,
so a peer can become preferred for `Query` while staying unremarkable for
`Command`.

```bash
ntl status
```

```text
routing model
  decisions   3 sampled
  delivered   66.7%
  exploration 0.0%
  pending     33.3%
```

Those last two lines are the model's health check:

- **exploration near zero** — the node has stopped trying alternatives, so it
  can no longer discover a better path. (With only one eligible synapse there
  is nothing to explore, and `ntl status` will not warn.)
- **pending near 100%** — no receipts are arriving, so the weights reflect
  nothing. Usually it means peers are emitting `best-effort` traffic only.

## See It Learn

The two-node exchange above moves a weight once. To see the model actually
separate a good peer from a bad one:

```bash
cargo run -p ntl-example-two-node-learning
```

```text
Phase 1 — both peers deliver. Both weights rise.
  round     peer A     peer B  chosen
      1     0.1450     0.1450  A B*
     12     0.6400     0.6400  B* A

Phase 2 — peer B starts refusing every signal.
  round     peer A     peer B  chosen
      1     0.6850     0.6175  A B✗*
     12     1.0000     0.3700  A B✗*

  The refusing peer lost weight; the delivering peer kept it.
  Nothing configured that. The only input was the receipts.
```

The `*` marks an exploratory choice. Note that peer B keeps being tried even
after it starts failing — that is deliberate, and it is what lets B recover
if it starts working again. A router that stopped probing a failing path
could never notice it had recovered.

The demo advances a simulated clock by an hour per round, because a
per-identity influence cap bounds how much one peer can move a weight inside
one window. Learning is rate-limited on purpose; see
[learning-model](/spec/learning-model) §2.4.

## Running a Long-Lived Node

```bash
ntl start --dev
```

`--dev` binds loopback only, so a development node is not reachable from the
network by accident. For a real deployment use `ntl start --listen
0.0.0.0:4433 --peer <addr>`, or the `ntl-node` / `ntl-edge` binaries, which
read `$NTL_HOME`, `$NTL_LISTEN`, and `$NTL_PEERS`.

## What Is Not Built Yet

Being explicit, so you do not go looking:

| Not yet | Notes |
|---|---|
| Public test network | No bootstrap nodes are running. Connect nodes you control. |
| Rust crates on crates.io | Install via npm or `cargo install --git`. |
| Post-quantum crypto | The interface is specified and pluggable; the shipping module is Ed25519. See [crypto-interface](/spec/crypto-interface). |
| QUIC transport | Currently TCP with length-prefixed CBOR frames. |
| PostgreSQL backend | Trait and config are defined; use SQLite. See [storage backends](/guides/storage-backends). |
| Payload encryption | Signals are signed, not encrypted. |
| Adapters | Web2, Web3, and legacy adapter crates are stubs. |
