NTL does not ship a database. It specifies what a node must remember and
leaves where to a backend you choose.

**NTL runs on the databases you already trust.** If you operate PostgreSQL,
point NTL at it. If you are deploying to a phone or a sensor, SQLite needs no
configuration at all.

<Note>
The contract every backend satisfies is
[spec/storage-interface](/spec/storage-interface). The Rust expression of it
is the `NodeStore` trait in
[`ntl-core`](https://github.com/openNTL/ntl/blob/main/runtime/ntl-core/src/store/mod.rs).
</Note>

## Choosing a Backend

| Backend | Best for | Durability | Status |
|---|---|---|---|
| **SQLite** | Edge nodes, single-machine full nodes | Survives power loss (WAL) | Shipping — the default |
| **PostgreSQL** | Full nodes in existing Postgres estates | Survives power loss | Planned |
| **In-memory** | Tests, `--dev`, ephemeral nodes | None | Shipping |
| **Graph databases** | Deployments where topology *is* the data | Backend-dependent | Via the trait |
| **KV stores** | Dedup cache and hot state offload | Backend-dependent | Via the trait |

If you are unsure, use SQLite. It handles both edge and full-node
deployments, and moving later is a configuration change plus a migration,
not a rewrite.

## SQLite (Default)

Zero configuration. `ntl init` creates the database and applies migrations
on first run.

```toml
[storage]
backend = "sqlite"
path = "~/.ntl/node.db"      # a single file
```

Full options:

```toml
[storage]
backend = "sqlite"
path = "~/.ntl/node.db"
journal_mode = "wal"          # default; keeps readers unblocked by writers
synchronous = "normal"        # normal | full | off
busy_timeout_ms = 5000
retain_signal_history = false # default off — payloads are sensitive
```

### Why SQLite Is the Edge Story

A single file with no server, no socket, and no configuration is exactly what
a constrained device needs. WAL mode lets the propagation path read synapse
weights while the learning loop writes them, without either blocking the
other.

On flash-backed devices, `synchronous = "normal"` trades a narrow
power-loss window for materially fewer write cycles. Use `full` where power
loss is likely and the hardware can take the wear.

<Warning>
Do not put the database on a network filesystem. SQLite's locking is
unreliable over NFS and SMB, and the failure mode is corruption rather than
an error.
</Warning>

## PostgreSQL

For operators who already run PostgreSQL and want NTL state alongside
everything else — shared backup, monitoring, and access control.

```toml
[storage]
backend = "postgres"
url = "postgres://ntl@localhost/ntl"
max_connections = 16
schema = "ntl"                # keeps NTL tables out of `public`
```

<Note>
**Status: planned.** The trait and configuration surface are defined and the
crate is stubbed; the implementation is not complete. Use SQLite today.
</Note>

Because `NodeStore` is synchronous while Postgres drivers are asynchronous,
`ntl-store-postgres` wraps its calls in a blocking pool at the crate
boundary. That choice keeps `ntl-core` free of an async runtime — see
[storage-interface](/spec/storage-interface) for the reasoning.

## In-Memory

For tests and ephemeral nodes.

```toml
[storage]
backend = "memory"
```

`MemoryStore` in `ntl-core` is the **reference implementation** — the
semantics every other backend is checked against. Nothing survives process
exit, so a node using it re-bootstraps from its configured peers and relearns
its weights from scratch.

## Graph Databases

A node's synapse topology is a weighted graph, so a graph-native backend can
store it as one — making queries like "which paths within three hops have
carried `Query` signals successfully" a native traversal rather than a join.

Any graph database can back NTL by implementing `NodeStore`: Neo4j,
Memgraph, or a graph layer of your own. Nothing in the protocol privileges
one.

Where the backend supports it, the storage graph and the synapse topology can
be *the same graph*: signals deposit state as they propagate, and state
changes emit signals. This is a capability of such backends, not an
assumption NTL makes.

## KV Stores

The deduplication cache is the one piece of node state that is naturally a
TTL-keyed KV workload, and Redis-style stores do it better than a relational
table.

A backend MAY serve the dedup cache from a KV store while keeping synapse
and journal state elsewhere — but the atomic check-and-set requirement in
[storage-interface](/spec/storage-interface) §3 still applies. Redis `SET
key NX EX` satisfies it; a `GET` followed by a `SET` does not, and the race
it admits is duplicate propagation.

## SiafuDB

[SiafuDB](https://siafudb.org) is a swarm-based graph database, also
stewarded by The Bundu Foundation. It is **one ecosystem backend among
several**, not a dependency of NTL, and NTL does not require it.

Its Graph Sync Protocol is a natural fit for NTL's learning loop: sync
acknowledgements are exactly the delivery outcomes the routing model trains
on. That makes it a good worked example of the general pattern described in
[research/02](/research/02-machine-learning-principles) — not a special
case the protocol accommodates.

```toml
[storage]
backend = "siafu"
endpoint = "siafu://localhost:7700"
```

<Note>
**Status: planned**, behind the `siafu` feature flag. SiafuDB is itself in
development. NTL's roadmap does not depend on it.
</Note>

## Writing a Backend

Implement `NodeStore` and run the conformance suite:

```rust
use ntl_core::store::{conformance, NodeStore};

#[test]
fn my_backend_conforms() {
    let store = MyBackend::open_temporary().unwrap();
    conformance::run_all(&store);
}
```

The suite is public API precisely so out-of-tree backends can hold
themselves to the same semantics as the in-tree ones. It checks the two
requirements backends most often miss:

1. **Deduplication is one atomic check-and-set.** A read then a write leaves
   a race, and that race is duplicate propagation.
2. **Outcome resolution is idempotent.** The first receipt wins; a second
   must not overwrite it. At-least-once delivery makes duplicate receipts
   routine.

Passing the suite is necessary but not sufficient — the concurrency and
durability requirements are not fully mechanically checkable. Read
[spec/storage-interface](/spec/storage-interface) before shipping.

## Migrating Between Backends

There is no migration tool yet. What works today:

1. Stop the node.
2. Export via the new backend's own tooling, or accept the relearning cost.
3. Update `[storage]` and restart.

Relearning is survivable but not free: the node keeps its identity and
configured peers, and reconverges on weights over hours to days depending on
traffic. Plan a migration for a quiet period, and expect degraded routing
quality until the model catches up.
